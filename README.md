## What This Does

This is an agent that gives fashion advice as well as creating captions. A user 
is able to ask the agent for a specific clothing they are looking for. They are
able to get advice on whether to buy certain items. They can also automatically
create a caption once an item has been bought.

---

## Tool Inventory

### `search_listings`

**What it does:**

Takes in a user's general description and finds similar items within the dataset.

**Inputs:** 

Takes in three parameters. The first is 'description' which is a string and is 
required. This description can include a brand but is not needed. The second parameter 
is 'size' which is also a string and is a optional parameter. It is not case sensitive 
and can be passed as 'None' to skip. The third parameter is 'max_price' which is a
float and is also an optional parameter. It can be passed by passing 'None'.
  
**Returns:**

Returns a list of dictionaries. each dict has the following fields:
id, title, description, category, style_tags (list), size, condition, 
price (float), colors (list), brand (str or None), platform. 

**When it has nothing:**

If nothing matches a empty list will will be returned.

### `suggest_outfit`

**What it does:**

Suggests outfits based on a user's wardrobe and a new potiential clothing item.

**Inputs:**

Takes in two parameters. The first is a listing dictionary which contains
the item the user is considering to buy. The second parameter is a 
dictionary with the key 'items'. These items are clothing items a user
owns. This dictionary may be empty.

**Returns:**

Returns a string of a potiential outfit based on the information it was given. 

**When it has nothing:**

If the dictionary that contains a user's clothing items is empty it will give
general styling advice.

### `create_fit_card`

**What it does:**

Creates a caption based on the chosen outfit.

**Inputs:**

Takes in two required parameters. The first is 'outfit' which is a string from 
suggest_outfit(). The second parameter is 'new_item' which is the listing dict 
for the item.

**Returns:**

A string containing 2 - 4 sentences representing a caption.

**When it has nothing:**

Returns a descriptive message.

---

## Planning Loop

**Branch rule:**

If the string 'description is emtpy in search listing then stop session and ask 
user for a proper explanation of the item that want. 
If the dictionary containing a user's clothing items is empty put a message in
the session asking for more information on their clothing items. Once items have
been given run suggest_outfits() and pass result onto create_fit_card.

**Where it lives:** `agent.py::run_agent`

**How the query is parsed:** Regex (`re` module in `_parse_query`), extracting price ceilings (e.g. `under $30`), size filters (e.g. `size M`), and cleaning conversational phrases to isolate description keywords.

**What moves through the session:**
1. `query` (str) & `wardrobe` (dict) initialize the session via `new_session()`.
2. `parsed` (dict): Extracted `description`, `size`, and `max_price`.
3. `search_results` (list[dict]): Matching listing dictionaries returned by `search_listings()`.
4. `selected_item` (dict): The top listing dictionary chosen from `search_results` (or `error` set if empty).
5. `outfit_suggestion` (str): Styling recommendations returned by `suggest_outfit(selected_item, wardrobe)`.
6. `fit_card` (str): Final 2–4 sentence caption generated by `create_fit_card(outfit_suggestion, selected_item)`.

## How I Used AI

**Moment 1**

- *What I asked for:* I was stuck on `run_agent()` in `agent.py`, so I pasted in the TODO comments and asked Claude to help me implement it. I specifically wanted it to parse the user's query with regex and handle the case where `search_listings` finds nothing.
- *What came back:* It gave me a working loop that called the tools one after another, but it just passed values straight from one call into the next. Nothing was saved to or read from `session`. And when the search came up empty, it set `session["error"] = "No results found"`, which doesn't tell the user anything useful.
- *What I changed:* I rewrote it so every tool's result gets written to `session` and then read back out for the next call. That way I can actually see what state the agent is in at each step. I also changed the empty-search branch to look at what was searched for and suggest something concrete, like raising the price ceiling or using broader search terms, instead of just hitting a dead end.

**Moment 2**

- *What I asked for:* I wanted to know what makes a fit caption feel real and worth posting on Depop or Instagram, and how I could turn that into acceptance criteria I could actually check for `create_fit_card`.
- *What came back:* Claude broke it down into a few things: start with a hook that grabs attention, mention details you can feel (texture, wash, fabric, something unusual about the piece), keep it short at 2 to 4 sentences, and work the price and platform in naturally.
- *What I changed:* I turned that advice into two criteria in `criteria.md`. Criterion 4 requires specific details like color, texture, or pattern, and Criterion 5 requires an opening hook. Then I rewrote the prompt in `create_fit_card()` in `tools.py` to spell out those same requirements, including a hard limit of 2 to 4 sentences.

**Moment 3 (Unit 4)**

- *What I asked for:* After discovering in the Unit 4 before-evaluation that four out of five runs for the flannel shirt generated the exact same cliché opening ("Channel your inner 90s icon with..."), I asked AI how to prevent model repetition and cliché template collapse across repeated generation calls on the same item without lowering temperature or making the caption read robotically.
- *What came back:* Claude recommended negative constraint prompting—explicitly listing forbidden stock openers (e.g. "Channel your inner...", "Stop scrolling...", "The holy grail...") while instructing the model to vary sentence structures and opening approaches (sensory details, bold claims, questions).
- *What I changed:* I incorporated negative constraints directly into guideline 2 of `create_fit_card` in `tools.py` while explicitly prompting for varied sentence structure. Re-running the evaluation confirmed that zero out of five tries repeated the "Channel your inner..." cliché, successfully increasing lexical and stylistic diversity across runs.

## What's Still Broken

While all five formal benchmark criteria scored 5/5 on the evaluation suite, an honest inspection of the system reveals several remaining failure modes and architectural limitations:

1. **Residual Opening Pattern in Fit Cards (Criterion 5 edge case):**
   - *What happens:* While the negative constraints introduced in Milestone 5 successfully eliminated the `"Channel your inner..."` cliché across all 5 runs, the model gravitated toward another recurring opening phrase: three out of five runs for the flannel shirt began with `"Nothing beats the..."` (*"Nothing beats the heavy, lived-in feel..."*, *"Nothing beats the heritage warmth..."*).
   - *What I'd do:* Negative constraint lists are reactive and cannot anticipate every stock pattern. A complete solution would dynamically inject distinct stylistic angles per call (e.g. alternating between historical context, garment texture, and bold styling takes) or track recently generated openers in session state to enforce a cross-call n-gram uniqueness penalty.
   - *Why I stopped:* Implementing cross-call memory or dynamic angle injection requires expanding the session schema and changing the stateless signature of `create_fit_card`. The single prompt constraint was the highest-leverage targeted change for this unit.

2. **Fragile Regex Query Parsing (`agent.py`):**
   - *What happens:* `parse_query()` uses regular expressions to extract `max_price` and `size`. It cannot understand compound constraints ("under $30 excluding shipping"), price ranges ("between $20 and $30"), negative filters ("no crop tops", "not distressed"), or colloquial expressions ("around twenty bucks"). Any non-standard phrase either gets dropped or stays stuck inside the search description.
   - *What I'd do:* Replace regex matching with an LLM structured extraction step or a formal intent parser that converts natural language into a validated JSON filter schema before invoking `search_listings`.
   - *Why I stopped:* Regex was sufficient for all defined benchmark scenarios. Adding an LLM call ahead of the search step introduces additional latency and cost for every turn.

3. **Greedy Single-Item Selection (`agent.py`):**
   - *What happens:* When `search_listings` returns multiple relevant items, the agent blindly selects `search_results[0]` to style. It does not compare the candidate items against the user's specific wardrobe to see which piece would yield the most versatile or cohesive outfit.
   - *What I'd do:* Add an intermediate selection step that scores candidate items against the wardrobe's dominant styles, colors, and gaps before passing the winner to `suggest_outfit`.
   - *Why I stopped:* The course architecture prescribes a three-tool sequence (`search_listings` -> `suggest_outfit` -> `create_fit_card`). Modifying the control flow to include multi-item candidate evaluation would exceed the scope of the unit.

4. **Empty Wardrobe Styling Depth (`tools.py`):**
   - *What happens:* When a user has an empty wardrobe (`--empty-wardrobe`), `suggest_outfit` falls back to general styling advice since it has no personal garments to pair against. While it prevents crashes, it cannot offer concrete outfit recipes.
   - *What I'd do:* In empty-wardrobe mode, have the agent search the listings catalog for 2–3 complementary items to build a complete starter capsule around the selected piece.
   - *Why I stopped:* The unit requirement was to gracefully handle the empty wardrobe failure mode without erroring out. The general advice fallback met that requirement cleanly.

## Capstone

**What This Extends**

This capstone extends **FitFindr**, the autonomous fashion styling and thrift discovery agent built in Units 3 and 4. In its original form, FitFindr took search queries for new clothing items, retrieved candidate listings over MCP, evaluated whether to buy them against an existing wardrobe (`suggest_outfit`), and generated social captions (`create_fit_card`).

What is new is the **Wardrobe-Aware Occasion Stylist**: an intelligent styling capability that takes an occasion (e.g., *"casual Sunday brunch"*, *"tech interview"*, *"rainy outdoor concert"*) and an existing wardrobe inventory, evaluates formality and practical requirements, strictly selects coordinating garments from what the user already owns across multiple categories (tops, bottoms, shoes, outerwear/accessories), and provides a grounded rationale citing the specific colors, materials, and style tags of the selected pieces. Crucially, it incorporates negative guardrails to detect and reject occasions that the wardrobe cannot fulfill (such as formal black-tie events for an all-streetwear closet), rather than hallucinating non-existent items or making inappropriate suggestions.

**The Shape**

**Shape C — Extend ONE capability.** 

The extension adds one new operational agent capability: occasion-based outfit recommendation grounded exclusively in a local wardrobe repository.

*What is out of scope:*
1. **Interactive terminal menu loops:** We are not building a multi-step interactive CLI questionnaire, curses interface, or CRUD menu. The extension runs directly via a single deterministic CLI command.
2. **Dynamic wardrobe mutation:** We are not adding interactive features to add, delete, or edit wardrobe items on disk during a session. The wardrobe schema remains a clean, validated JSON datastore.
3. **Computer vision and visual outfit rendering:** We are not integrating image generation (e.g. Imagen/DALL-E) or computer vision analysis of clothing images. All styling reasoning is performed on structured textual metadata.
4. **Third-party live weather or calendar APIs:** We are not pulling live weather conditions or syncing Google Calendar events; occasions are supplied directly as natural language prompts.

### Diagnosis of Missed Criterion

**Criterion 4 Missed (0/5 across Runs 1, 2, and 3):**
- **Stage:** Caching subsystem (`generate.py::_cache_read`) and token instrumentation delta calculation (`occasion_stylist.py::_finalize`).
- **Mechanism:** In `config.py`, `CACHE_ENABLED` is set to `True` by default for interactive development. When `eval_capstone.py` was executed, repeated queries with identical prompt strings hit `config.CACHE_DIR/*.json`. While response text was recovered instantly (yielding sub-millisecond durations of `0.0001s`), `generate.py` only cached the string response:
  ```python
  {"response": response}
  ```
  It did not persist token metadata in the cache file, nor did it increment `_prompt_tokens` and `_output_tokens` on a cache hit. As a result, `token_counts()` before and after the call returned identical values (`tokens_diff["total"] == 0`). Because Criterion 4 required `has_tokens = tokens_diff["total"] > 0` to verify observability, every single cached test run failed the token presence check and was scored as a miss (`0/5`), despite being under 2.5 seconds.
